  Is Graphiti useful for production?

  Honest assessment:

  - What it adds: Entity relationships, temporal facts, deduplication — things
  vector search can't do
  - What it costs: ~100 LLM calls per document, 20-30 min per PDF, known parsing
   bugs (#879/#882)
  - The catch: Hybrid search actively deduplicates graph results that overlap
  with vector results — meaning much of what graph finds, vector already found

  My take: For most RAG use cases, vector search alone (Qdrant) gives 90% of the
   value at 1% of the cost. Graphiti is worth it only for:
  - Documents where relationships between entities matter (contracts,
  regulations, org charts)
  - Use cases needing temporal queries ("what changed since X?")
  - When you can afford the ingestion time and LLM cost

  The real question: Do you need a KG at all?

  Most production RAG systems ship with vector search only. A KG adds value
  specifically when:
  - You need multi-hop reasoning ("Who reports to the CEO of company X?")
  - You need temporal tracking ("What changed since last quarter?")
  - Your docs have dense entity relationships (contracts, regulations, org
  structures)

  My recommendation for Spektr

  Option A — Drop Graphiti, keep it simple: Your vector search already works.
  Make GRAPH_ENABLED=false the default. Most users won't need it.

  Option B — Replace with LightRAG: Similar quality, faster, incremental
  updates, lower LLM cost. Better maintained community.

  Option C — LLM-free extraction: Use SpaCy NER + rule-based relationship
  extraction. Zero LLM cost, 94% quality, processes in seconds not minutes. Add
  results to Neo4j yourself.

  CPU-friendly options (no GPU needed)

  Tool: SpaCy (en_core_web_lg)

  CPU Speed: Very fast, milliseconds

  ────────────────────────────────────────
  Tool: GLiNER2

  CPU Speed: Fast on CPU
  Capabilities: NER + relation extraction + structured output, zero-shot (any
    entity type)
  Maturity: NAACL 2024, active community
  ────────────────────────────────────────
  Tool: Relik
  Size: ~1GB
  CPU Speed: Slow on CPU (~10-50x slower than GPU)
  Capabilities: NER + relation extraction, SOTA quality
  Maturity: Academic, GPU-oriented

  Verdict for your setup (no dedicated GPU)

  GLiNER2 is the sweet spot. It's:
  - 205MB — tiny, runs fine on CPU
  - Does both NER and relationship extraction in one model
  - Zero-shot — you define entity types at query time (no retraining needed)
  - Schema-driven output → easy to write directly to Neo4j
  - Active community, pip-installable

  SpaCy is faster but only does NER (no relationships). You'd need to pair it
  with co-occurrence heuristics or dependency parsing for relationships — more
  code, weaker results.

  Relik is the best quality but really wants a GPU. Without one, it's slow
  enough that you might as well use LLM calls.

  What this would look like in Spektr

  Current:  chunks → Graphiti (LLM calls) → Neo4j     [29 min]
  Proposed: chunks → GLiNER2 (CPU, local) → Neo4j      [seconds]

  - Replace GraphitiWriter with a GLiNERGraphWriter
  - GLiNER2 extracts entities + relations from each chunk
  - Write directly to Neo4j with Cypher (you already have _LegacyGraphWriter
  doing this)
  - No API calls, no cost, runs anywhere

  The tradeoff: GLiNER2 quality is good but not as rich as Graphiti's LLM
  extraction (no temporal reasoning, no entity deduplication across documents).
  But for 99% faster at zero cost, that's usually worth it.
